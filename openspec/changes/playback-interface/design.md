## Context

本文记录 playback-interface 阶段的接口与后端设计建议。用户后来要求实现后端，native-playback 已接续提供可选内置实现与终端接入，实际模块、依赖版本和验证以该变更为准。下文未实施的表述指当时的接口阶段；基础接口现在仍可单独以标准库构建。

本文分别记录已有接口契约与推荐的后续实现设计。用户补充了快进、快退需求，SeekTarget 和 seek 已声明到 Rust 源码。推荐后端、内部线程和持续故障恢复均未写入 Rust 实现，也不作为已经完成的播放验证。

## Goals / Non-Goals

**Goals:**

- 独立声明播放控制、音频来源和状态，调用方无需知道解码器或音频设备细节。
- 播放库和主程序由 workspace 统一检查，保持现有二进制发布方式。
- 细化后续内置实现的职责、资源所有权、加载提交、错误恢复与验证方式。
- 以一个时间定位方法覆盖指定时间跳转、快进和快退，并说明位置、状态与失败约定。

**Non-Goals:**

- 不接入解码、设备输出、播放线程、SQLite、终端界面或 NCM 解包。
- 不提供默认成功的播放器、模拟后端或播放队列；后端选型在本文记录为推荐，不增加 Cargo 依赖。

## Decisions

### 已确认：根二进制包与播放库组成 workspace

保留根包 `muse`，增加 `crates/muse-playback` 成员及 path 依赖。两者共用锁文件、构建目录、工具链及 AGPL-3.0-only 许可证。播放库是内部 crate，设置 `publish = false`、cargo-release 的 `release = false`，应用继续按现有版本与 Git 标签发布。

### 接口设计：可拥有的音频来源

`AudioSource` 要求 `Read + Seek + Send + 'static`，通过 blanket impl 接受文件、内存游标或其他拥有自身生命周期的读取器。`load` 接收 `Box<dyn AudioSource>` 并转移所有权。它承载完整的已编码音频，而不是 NCM 容器或 PCM；库不知道歌曲 ID 或数据库位置。

选择读取器避免固定要求文件缓存或整首音频加载到内存。当前存储的 `Library::open_audio` 已返回 `Cursor<Vec<u8>>`，关闭库连接后仍然可读，能够作为输入。将来可换成拥有型临时文件读取器，而不改变播放 trait；借用数据库连接的 BLOB 不能直接作为长期持有来源。

### 接口设计：小型控制 trait 与状态快照

当前 Rust 中的 `Playback` 声明 `load`、`play`、`pause`、`stop`、`seek`、`status`，错误采用受标准 `Error` trait 约束的关联类型。接口可通过 `dyn Playback<Error = E>` 使用，不把任何具体后端的类型写进 trait。方法不提供默认实现。时间定位声明与公开文档已补齐，下文记录其契约及后续实现要求。

- `load` 成功后处于 Ready、位置归零，不自动播放；失败返回错误，新来源不能被报告为成功加载。
- `play` 从已加载来源开始或恢复播放；没有来源时返回错误。重复播放调用保持幂等。
- `pause` 暂停当前播放并保留位置，对已经暂停或非播放状态保持幂等。
- `stop` 保留已加载来源并归零，状态回到 Ready；空来源保持 Empty。
- `seek` 完成绝对或相对时间定位并返回实际落点，状态和边界依照下文约定。
- `status` 返回状态、当前位置及可缺省的总时长，查询不触发播放。自然结束为 Finished，下一首由主程序决定。

状态错误约定属于未来实现的接口契约。接口的编译与调用方使用检查不等同于播放行为验证。本轮声明 seek；音量、设备选择与事件订阅仍待实际需求。

### 工程接入：覆盖 workspace

Makefile 和 CI 的 Clippy、测试及 release 构建显式覆盖 workspace，文档示例也进行编译。现有应用包版本、打包路径和标签校验保持现有格式，无需调整打包脚本。workspace 的合并发布提交消息使用固定文本，避免多包模式无法展开单包版本占位符；版本仍由 Git 标签标识。

### 本轮推荐：一个内置 Adapter，保持小型 Interface

播放 Module 负责一个已编码来源的解码、输出、控制、时序和资源释放。Interface 继续使用 `AudioSource`、`Playback`、`PlaybackState`、`PlaybackStatus`；后续内置 Adapter 建议命名为 `NativePlayback`，实现 `Playback<Error = PlaybackError>`，提供 `NativePlayback::open_default() -> Result<Self, PlaybackError>` 构造入口。该构造器和错误类型目前不存在于 Rust 源码。

歌曲 ID、选中歌曲、当前歌曲与待加载歌曲的映射，由应用层维护；数据库打开、NCM 解包、歌词封面读取也由既有模块负责。播放 crate 不依赖 `muse-library`、SQLite、Ratatui 或 NCM 类型，不决定下一首。当前输入限定为完整本地 MP3/FLAC，NCM 仍先由导入解包。

不为一个内置后端增加后端注册表、公开解码器 trait 或设备 trait。需要的可替换性已经集中在 `Playback` 这个 Seam；后续真实需求产生第二种 Adapter 时，再决定是否增加内部抽象。用户要求的快进快退由 seek 覆盖；音量、设备选择与事件订阅暂不扩展公开表面。

### Interface 设计依据：从上层操作核对底层保证

先列出应用的实际操作及必须观察的结果，再检查音频后端是否能直接提供这些保证。底层已有的方法可以帮助实现，但不自动成为公开接口；公开约定也不能超过底层及适配代码能够验证的能力。

| 上层需求 | Interface 表达 | 底层与 Adapter 的责任 |
| --- | --- | --- |
| 选中一首歌曲并准备播放 | `load(Box<dyn AudioSource>)` | 接收输入所有权；成功意味着来源可播放、Ready 且归零；未真正准备好不能返回完成成功 |
| 播放、暂停或恢复 | `play`、`pause` | 保留播放意图及正确位置，重复操作幂等；设备或解码错误返回可理解的原因 |
| 停止后能够重新播放当前歌 | `stop` | 成功归零并保留来源；不能直接继承清空来源的底层停止语义 |
| 快进、快退或跳到指定时间 | `seek(SeekTarget)` | 按执行时的位置计算相对移动，完成定位并返回实际落点，保持播放或暂停意图 |
| 显示进度和状态 | `status` | 短时读取完整快照；未知时长为 None，预读不推动播放进度；不能把错误当正常曲终 |
| 操作失败后更新界面 | `Result`、后续状态及错误契约 | 说明失败后保留的来源和恢复入口，保留错误阶段与原因，不要求界面检查 Rodio/CPAL 类型 |
| 保持终端可交互 | 应用后台控制流程 | 同步 trait 的完成返回在工作线程等待；提交请求与完成操作分开，界面只在完成确认后更新当前歌曲 |

因此 trait 文档需要同时说明输入所有权、成功后的状态、失败后的来源、幂等性、可能阻塞和资源释放。仅有方法签名不足以指导上层，也不足以验证实现。

当前选取同步完成语义：`load` 的 Ok 表示准备完成，`play` 的 Ok 表示启动请求已由输出实现接受，不代表整首必定播放成功；后续故障由 status 报告。应用使用请求标识关联加载确认与待选歌曲，一次一个加载任务。未来如果有明确的非阻塞控制需求，应另行设计“请求已接受”的返回与完成通知，不能在保持现有文档的同时把 Ok 改成“已放入队列”。

输入的 Seek 是文件字节定位能力，不等于音频后端支持任意时间跳转。本轮时间定位约定见下一节；需要音量时再定义归一化范围、有限值校验和可读取的结果。若存在真实的后端或来源能力差异，再增加能力查询以控制界面是否可用；不提前为所有底层功能建 trait 或能力表。

### 已声明：一个 seek 方法覆盖快进、快退和时间跳转

用户要求补齐快进快退，并要求实施接口设计。以下公开类型和必需方法已加入 Rust 源码，仍不提供后端或默认实现：

```rust
pub enum SeekTarget {
    Absolute(Duration),
    Forward(Duration),
    Backward(Duration),
}

// Playback trait 中的必需方法：
fn seek(&mut self, target: SeekTarget) -> Result<Duration, Self::Error>;
```

Absolute 表示音乐时间轴上的指定时刻，供进度条等操作使用；Forward、Backward 表示相对于操作执行时当前位置的移动，供快进快退使用。例如前进或后退 10 秒只是应用给定的步长，不是 crate 固定规则。用枚举区分方向与绝对时间，避免负 Duration、整数单位不明或同时存在多个同义方法。此需求按跳转解释，持续倍速播放另有需求时再设计。

相对移动在播放实现内计算，不让界面先读取 status 再加减，因为播放可能在两次调用间推进。加减使用饱和运算；后退到开头之前落在零，有可靠总时长时前进或指定位置超过结尾按总时长截取。总时长未知时不使用库内标签估算边界，也不为了兑现一次跳转隐式完整扫描整首；无法定位则返回范围或不支持错误。

Ok 中的 Duration 是定位完成时的实际落点，可能因格式和后端精度与目标不同。它不是请求已排队的确认，也不承诺扬声器的精确发声时刻；播放继续后，应通过 status 获取新位置。定位不能触发下一首或替换来源。公开文档采用以下成功状态约定：

| 定位前状态 | 成功落在曲内 | 成功落在已确认曲终 |
| --- | --- | --- |
| Empty | 无来源，返回错误 | 无来源，返回错误 |
| Ready | 零位置保持 Ready，非零位置变为 Paused | Finished |
| Playing | Playing，从实际落点继续 | Finished |
| Paused | Paused，保留暂停意图 | Finished |
| Finished | Paused，之后 play 从实际落点恢复 | Finished |

Ready 仍表示来源在开头，不新增公开状态。Finished 的公开文档已扩展为正常播放到曲终或成功定位到已确认曲终；seek 回到曲内后变为 Paused，避免 play 按 Finished 的约定又从头开始。只在实现确认曲终时进入 Finished，不能以估计时长代替 EOF。

无来源、不支持定位或执行前的参数检查失败，返回错误并保留正常旧来源与原播放意图；原来正在播放的时间仍可自然推进。开始移动读取器、重置解码器后发生读取、解码或输出故障，不能承诺回滚到精确旧位置；按候选持续故障规则停止继续提交音乐并保留原因，等待成功 load 或 stop 恢复。已有持续故障时 seek 返回该故障，不隐式清除它。

内部定位需要找到目标附近的音频包、重置解码器并按需要解码/丢弃到实际落点，清除旧 PCM 和预读结果，重设计时锚点。位置按“实际落点 + 新输出的音乐帧时长”计数。每次定位更新内部读取版本，旧 PCM、EOF 和错误不得覆盖新位置；设备缓冲中已经提交的尾音不承诺瞬时撤回。Symphonia 的定位返回请求与实际时间戳，定位后需要重置解码器；包定位与精确音频帧定位有区别：[FormatReader::seek 官方说明](https://docs.rs/symphonia-core/0.6.1/symphonia_core/formats/trait.FormatReader.html#tymethod.seek)。具体版本仍在实施时确定。

后台应用按当前歌曲的请求版本提交定位；如果执行前已经换歌，应丢弃过期请求，不能把旧歌的快退应用到新歌。歌曲 ID 和应用请求版本仍由应用管理，不加入 Playback trait。

### 本轮修订建议：停止语义与正常、故障状态一致

之前“故障后 stop 成功进入 Empty”的方案会使同一操作改变来源保留方式，上层需要额外判断当前歌曲是否被清空。此处改为推荐统一保证：有来源时 stop 成功必须保留来源、清除故障、进入 Ready 并归零；无法重建或恢复输出时返回错误，持续故障保持。无来源时 stop 成功进入 Empty。清空来源如果以后成为上层需求，再提供明确的 unload 操作。

这使上层可以在任意成功 stop 后保留当前歌曲映射，不必依据底层故障类型猜测来源是否仍存在。该修订仍是设计建议，未新增 Rust 方法或更新强制规格。

```mermaid
flowchart LR
    Library["muse-library：完整已编码音频"] --> Source["Box&lt;dyn AudioSource&gt;"]
    Source --> Playback["muse-playback：NativePlayback"]
    App["muse：选择歌曲、后台控制"] -->|load / play / pause / stop / seek| Playback
    Playback -->|status / 错误| App
    Playback --> Decode["Symphonia 解码"]
    Decode --> Buffer["有限 PCM 缓冲"]
    Buffer --> Output["Rodio 输出 / CPAL 设备"]
```

### 本轮推荐：Symphonia 解码，Rodio 管理输出

| 方案 | 代价与契约适配 | 推荐状态 |
| --- | --- | --- |
| 直接使用 Rodio Decoder 与 Player | 接入短，但默认解码迭代器不能完整区分运行时错误和正常结束 | 不直接采用该解码路径 |
| 自己调用 Symphonia，PCM 交给 Rodio | 保留解码错误，再复用输出、设备配置及音频格式适配；需要私有 PCM Source | 首选设计 |
| Symphonia 与 CPAL 直接组合 | 完整控制错误和回调，但须自行处理设备格式、采样率转换及输出控制 | 如果首选桥接无法满足契约，再评估 |

调查以 Rodio 0.22.2 的官方文档与源码为依据，不将它写成已经锁定的项目依赖。Symphonia 提供 MP3/FLAC 解码能力；Rodio 的 `Player::append` 接受自定义 `Source`，设备构造器支持输出错误回调。来源：[Symphonia](https://github.com/pdeljanov/Symphonia)、[Rodio Player](https://docs.rs/rodio/0.22.2/rodio/struct.Player.html)、[设备错误回调](https://docs.rs/rodio/0.22.2/rodio/stream/struct.DeviceSinkBuilder.html#method.with_error_callback)。

Rodio 0.22.2 的 Symphonia 解码迭代器使用 `next_packet().ok()?`，并将部分解码失败转为 `None`；从外层仅观察迭代结束或队列为空，无法可靠判断此次结束是否由故障导致。这是读取官方源码后对适配方式的判断。因此建议由私有解码路径显式产出正常结束或错误，再向输出提供 PCM。来源：[Rodio 解码器源码](https://docs.rs/rodio/0.22.2/src/rodio/decoder/symphonia.rs.html)。

`AudioSource` 继续只要求 `Send`。如果选用的底层接口额外要求 `Sync`，在私有来源包装中用 `Mutex` 安全承载原读取器，并由解码线程独占读取；不使用不安全的 `Sync` 声明，也不将底层约束扩大为公开 trait 的要求。Rodio 自身 Decoder 的构造约束包含 `Sync`：[Decoder 文档](https://docs.rs/rodio/0.22.2/rodio/decoder/struct.Decoder.html)。

### 本轮推荐：私有模块布局与所有权

以下是后续实现的职责布局，不在本轮创建这些文件；文件只在有对应实现时拆分。

```text
crates/muse-playback/src/
  lib.rs              现有 trait、状态与公开类型导出
  native/
    mod.rs            NativePlayback、控制确认、来源替换
    decode.rs         来源包装、探测、MP3/FLAC 解码、时间定位和重建
    output.rs         PCM Source、Rodio 句柄、设备错误、输出计数
  error.rs            后端公开错误与内部持续故障
```

- `NativePlayback` 管理当前会话及设备生命周期；来源与解码器由后台解码工作持有，保留足以重新建立解码器的输入所有权。
- 解码结果放入按帧数限制的 PCM 缓冲；建议先用约 250ms 的上限进行验证，实际值按测试调整。暂停或 Ready 状态预读达到上限就等待，不持续增长或解码整首 PCM。
- Rodio 只消费已准备的 PCM。自己的音频 Source 热路径不访问 SQLite、文件或终端，不等待解码线程，也不执行工作线程 join。缓冲暂时为空时输出静音并保留播放意图，不将欠载当作自然结束。
- 内部来源和设备事件分别带会话版本，只允许当前版本更新状态；取消或替换后到达的旧曲终、旧错误不能影响新来源。

### 本轮推荐：加载先准备，成功后替换

`load` 的推荐完成条件是：新来源归零并成功探测、至少得到有效音频帧、有限缓冲和可用输出已经准备好，最后提交为新会话并返回 Ready。它不代表已经验证整首音频，后续坏帧或读取故障仍可能发生。

准备候选来源时，正常旧会话继续保持原播放或暂停意图；只在准备成功后停止旧会话、替换来源并归零。失败释放候选来源并返回错误，不更新应用的当前歌曲 ID。若同时发生真实设备故障，则按持续故障处理，不能承诺失效设备上的旧歌曲继续发声。`load` 失败仍已消费输入所有权，调用方重试时重新从库打开来源。

正常 `stop` 保留输入、清空待输出 PCM，从字节零重新建立解码状态后回到 Ready；Finished 的 `play` 使用同样的重建能力从头开始。不把 Rodio 清空输出队列的 `stop` 直接当作 muse 的来源保留语义。回读或重建失败返回错误并进入持续故障，不能宣称已经 Ready。

### 本轮推荐：状态、持续错误与资源释放

继续使用现有五个公开状态，持续故障由 `status` 的 `Err` 表达。具体后端错误建议区分无来源、输入读取、格式不支持、定位不支持或失败、解码、设备输出和工作线程异常；保存阶段及原始错误原因。内部可用 `Arc` 保留故障，每次查询构造错误包装，不要求 `Playback::Error` 实现 Clone。恢复规则见后面的候选失败表，尚不是公开 Rust 文档中的保证。

`position` 根据实际被输出路径消费的音乐帧换算，不按加载时间或解码进度估算；预读、暂停、Ready 及欠载填充的静音不推动位置。`duration` 采用解码器可靠提供的总时长，未知时为 None，不为获取时长完整扫描整首音频。正常结束需要解码路径确认 EOF 且音乐 PCM 已交给输出；错误优先于 Finished。设备缓冲和重采样预读带来短暂偏差，不将快照承诺为扬声器实际发声的精确时刻。

销毁时先停止继续提交音乐，再取消后台解码并释放来源及设备句柄；不使用让音频继续播放的 detach。故障后的 stop 保留输入，尝试重建解码和输出，只有恢复成功才清除故障；load 成功则替换并释放旧来源。音频线程不负责等待自身退出。清理需要来源读取能返回；任意自定义 `Read` 如果无限阻塞，就无法承诺固定时间内 join。因此第一版使用已有内存来源或稳定本地拥有型读取器，不提供网络输入。

### 本轮推荐：构建与应用接入

后续实现建议以 `native` feature 启用可选 Rodio/Symphonia 依赖和 `NativePlayback` 导出；播放库默认 feature 仍只提供标准库 Interface。真正接入后，应用发布默认启用内置播放；当前 Cargo 配置不改变。

构造和可能较慢的 `open_audio`、`load`、seek、停止后的重建在应用播放工作线程进行，TUI 不直接等待同步 trait 返回。应用单独展示“正在加载”，保留旧当前歌曲直到加载成功；一次接受一个加载任务。定位请求与完成结果关联当前歌曲版本，相对移动按执行时位置计算。`status` 读取短快照，不读音频或等待解码。工作结果经应用消息更新界面，不将 Loading 状态加入播放枚举。设备构造失败只影响播放，导入、浏览、备份继续可用。

CI 的基础 Interface 检查不需要设备；后续开启 native 的 Linux 构建需安装 ALSA 开发依赖。跨平台构建和无设备的解码/状态检查不等同于真实输出验证，物理设备上的播放、暂停、故障与释放要另做检查。依据：[CPAL Linux 构建说明](https://github.com/RustAudio/cpal#linux-build-dependencies)。

### 后续验证计划：从 Interface 检查真实行为

| 验证 | 必须观察的行为 |
| --- | --- |
| 库内 MP3/FLAC 及非 Sync 的 Send 来源 | 从库取得拥有型来源后移走原文件、关闭库，仍能加载；私有适配不扩大 AudioSource 约束 |
| 先播放旧曲，再加载坏输入 | 坏输入返回错误，旧来源与播放意图保留；加载成功才切换当前歌曲，候选来源释放 |
| 暂停、预读与欠载 | 位置按音乐帧计数，暂停或预读不推动位置；欠载静音不能被判为 EOF |
| MP3/FLAC 的绝对定位与连续相对移动 | 两种格式实际支持时间定位；返回真实落点，连续快进快退按执行时位置计算，不要求界面读取旧快照算目标 |
| 定位边界与状态 | 开头、结尾截取正确，未知时长不伪造边界；暂停不启动，Ready 非零定位与 Finished 回退变为 Paused，曲终不自动切歌 |
| 无来源、不支持或定位中故障 | 前置拒绝保留旧来源及播放意图；执行中无法恢复的故障持续报告，不假报成功或承诺精确回滚 |
| 定位后的旧缓冲与过期请求 | 旧 PCM、EOF、故障不覆盖新位置；换歌前提交的旧定位请求不能作用于新歌 |
| 自然结束与正常停止后重播 | 真实 EOF 且音乐缓冲排空后 Finished；重新 play 从头开始，stop 归零保留来源 |
| 中途读取、解码或设备故障 | 停止继续提交音乐，status 重复返回故障；错误不能被误报成 Finished；恢复只在成功 load 或候选故障 stop 后生效 |
| 替换、退出与旧事件 | 旧来源不再输出，旧事件不污染新会话；后台解码、有限缓冲、设备和来源均完成释放 |
| 三平台构建与物理输出 | Linux/macOS/Windows 构建覆盖依赖；物理设备另验发声、暂停、曲终和输出故障，不能以编译代替 |

错误来源测试可使用确实返回读取错误的拥有型 reader；PCM 测试消费真实解码结果，不增加默认成功的播放实现。具体缓冲预算和音频回调负载在这组验证中测量，尚未进行。

## Risks / Trade-offs

- 接口声明没有实际播放能力 → 不提供后端构造器，不在主程序接入占位实现。
- 音频来源的生命周期要求不能直接接受借用 BLOB → 后续存储实现负责来源所有权，不把 SQLite 类型暴露给播放库。
- 未来后端可能需要新的控制或事件 → 当前只确定基础控制，具体库选型与扩展在后续变更中处理。
- 原子替换准备期同时持有新旧来源 → 内存可能同时包含两首已编码歌曲，PCM 仍受缓冲上限约束，不承诺解决当前存储整首读取的峰值内存。
- 仅探测和首帧成功不能验证整首 → 运行时显式保留读取/解码故障；EOF 与截断的区分依赖格式和可用长度信息，不宣称所有截断都能检测。
- 自定义来源可能无限阻塞 → 第一版只接入可完成读取的本地拥有型来源，不承诺任意 Read 的有界取消。

增加 workspace 和内部库，刷新锁文件，调整 workspace 检查。没有历史音频数据迁移。回退时移除新增成员和 path 依赖，并恢复单包检查配置。

### 当前契约：成功操作的状态转换

下表整理现有接口已经声明的成功路径；没有来源时 `play` 返回错误。状态转换属于实现方需要遵守的约定，当前 crate 没有后端。

| 当前状态 | `load` 成功 | `play` 成功 | `pause` 成功 | `stop` 成功 |
| --- | --- | --- | --- | --- |
| Empty | Ready，位置归零 | 无来源，返回错误 | Empty | Empty |
| Ready | Ready，替换来源并归零 | Playing | Ready | Ready，位置归零 |
| Playing | Ready，替换来源并归零 | Playing，幂等 | Paused，保留位置 | Ready，位置归零 |
| Paused | Ready，替换来源并归零 | Playing，从当前位置恢复 | Paused，保留位置 | Ready，位置归零 |
| Finished | Ready，替换来源并归零 | Playing，从头开始 | Finished | Ready，位置归零 |

自然结束由 Playing 转为 Finished；seek 的成功状态转换见上文定位表，包括定位到已确认曲终后 Finished。`status` 只观察状态，不触发播放或切换来源。上述表格没有规定错误发生后的状态。

### 候选：加载失败保留旧来源，异步错误持续报告

建议增加以下失败契约，后续确定后再同步公开文档与规格。它不新增后端、状态枚举变体或控制方法。

| 情况 | 建议保证及恢复方式 |
| --- | --- |
| 新来源加载失败，原来有正常来源 | 返回错误并释放失败的新来源，保留旧来源及原播放或暂停意图；原来正在播放的来源继续正常推进，不承诺冻结其时间位置 |
| 新来源加载失败，原来为空 | 返回错误，保持 Empty，不把新来源报告为已加载 |
| 原来已处于持续错误，新来源加载失败 | 返回本次加载错误，原来的持续错误仍保留，不把失败加载当成恢复 |
| 同步控制操作失败 | 返回错误，不把请求的目标状态报告为操作成功；若同时发现不可继续播放的故障，则按持续错误处理 |
| 播放开始后发生不可继续播放的异步错误 | 停止音频输出，保留可再次报告的错误信息；`status` 持续返回错误，不将故障当作 Finished |
| 持续错误后重复查询、调用 `play`、`pause` 或 `seek` | 持续返回错误，不靠查询清除错误，也不从故障来源自动重新开始 |
| 持续错误后 `load` 成功 | 清除旧错误，替换来源，进入 Ready，位置归零，不自动播放 |
| 持续错误后 `stop` 成功 | 保留已有来源，重建成功后清除错误，进入 Ready 并归零；没有来源时进入 Empty，来源保留方式与正常 stop 一致 |
| 持续错误后 `stop` 失败 | 返回恢复错误，来源保留且持续故障保持，调用方仍可尝试加载新来源或销毁播放器 |

`status(&self)` 保持只读查询；持续错误由内部保留的故障信息表达，不要求关联错误类型实现 Clone，也不把错误作为一次性事件消费。故障后的 stop 成功可以直接重播已有来源；stop 无法恢复时，调用方可从库重新打开并加载，或销毁播放器。替换加载成功及销毁播放器都须释放旧来源和输出资源。

保留旧来源的方案让无效新文件不会打断正常播放，但要求后端在替换前准备新来源。另一方案是加载开始即释放旧来源，失败后保持 Empty；如果选定后端无法支持前者，应在接入前明确修改契约。当前两者尚未成为公开接口保证。
