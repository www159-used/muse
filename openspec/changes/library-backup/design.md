## Context

音乐库使用 SQLite 第 1 版结构，音频和附件均为 BLOB；成功导入记录参与去重。运行中开启 WAL。现有 `Library::open` 会初始化不存在的库，不适合作为备份来源的打开入口。

## Goals / Non-Goals

**Goals:** 提供包含已提交完整内容的单文件快照；验证库身份、结构版本、SQLite 完整性和外键；失败不发布半成品；无需终端即可备份和恢复。

**Non-Goals:** 自动迁移前备份、原地覆盖恢复、周期任务、压缩加密、播放后端及大文件读取优化。

## Decisions

以下均为本轮实现选择。

1. `Library::backup(destination)` 备份现有连接；`Library::restore(source, destination)` 只读打开已有库或副本，将其快照写入新路径。两个入口共享同一复制和验证流程。命令行的备份也使用只读入口，避免缺失源文件被初始化或源库被升级。
2. 使用 SQLite Online Backup API，分批复制页面，不加载整库音频到内存。复制前建立并读取源端只读事务，固定快照；其他 WAL 连接继续写入，其后来提交不进入该快照。曾考虑直接文件复制和 `VACUUM INTO`；前者不适用于运行中 WAL，后者增加重排整库数据的成本。
3. 在目标父目录下创建临时目录及文件；完成复制后检查库身份、当前结构版本、预期表字段、`integrity_check` 和 `foreign_key_check`，转为 DELETE 日志模式、关闭连接并同步文件，然后以不覆盖既有文件的方式发布。临时目录负责异常路径的数据库及日志清理。
4. 目标文件、符号链接或同名 `-wal`、`-shm`、`-journal` 任一存在即拒绝。发布时再次检查，不覆盖已存在目标。输出是独立单文件，不需要原日志。有限重试数据库锁冲突，超时报告错误；不限制正常大库复制耗时。
5. `muse --library <源库> --backup <副本>` 与 `muse --library <新库> --restore <副本>` 不要求 TTY。两项操作互斥，非法参数在数据库访问前失败；正常界面保持原入口。

备份采用 SQLite 官方在线备份机制：[SQLite Backup API](https://www.sqlite.org/backup.html)。发布采用 tempfile 的不覆盖接口：[persist_noclobber](https://docs.rs/tempfile/3.27.0/tempfile/struct.NamedTempFile.html#method.persist_noclobber)。

## Risks / Trade-offs

- 长时间读事务可能使运行中 WAL 增长 → 分页复制并在复制完成后尽早释放源端快照；不阻塞 WAL 写入，但暂时限制检查点回收。
- 备份需要接近整库大小的额外空间 → 页面复制失败时返回错误并清理临时目录，不发布目标文件。
- SQLite 完整性校验不是音频解码或全库内容哈希验证 → 测试验证已知音频和附件字节，以及恢复后的去重行为；不宣称发现所有人为篡改。
- 目标目录同步和文件系统断电语义因平台而异 → 关闭并同步完成的单文件再发布；保证正常错误和目标竞争时不覆盖，不宣称跨平台断电持久性保证。
- 其他进程未协调地创建同名日志文件仍可能竞争 → 发布前检查残留日志，拒绝正常可检测冲突；恢复到全新且不被其他进程操作的路径。

## Migration Plan

数据库结构仍为第 1 版。此变更只增加 API 和命令；移除新命令不影响原库。恢复输出保持源结构版本，打开时沿用现有存储初始化规则。
