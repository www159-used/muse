## Context

muse 已建立 Rust 工程、音乐库存储、本地导入与终端浏览。用户随后要求实现播放后端，native-playback 接续实现独立播放库和终端接入。用户希望仿 Neovim 的外观与操作方式，独立运行，并明确要求减少第一版功能。用户已接受 SQLite 同时保存歌曲信息与音频内容，确认使用 Rust 开发、默认递归导入目录，并优先适配网易云音乐的本地下载目录。

本文件记录讨论状态。文档通过格式校验不表示产品行为已经全部确定。

## Goals / Non-Goals

**Goals:**

- 打通导入、显示歌曲、选择播放的最小路径。
- 音乐库在导入成功后不依赖原始文件位置。
- 存储实现集中在一个模块中，对界面与播放器提供小而明确的接口。

**Non-Goals:**

- 不复刻 Neovim 的完整编辑器、插件或配置体系。
- 不在这一轮引入复杂音乐管理功能。
- 工程初始化由 `project-foundation` 完成，存储与导入由本变更建立；用户随后授权的真实播放由 `native-playback` 完成。复杂播放管理仍在范围外。

## Decisions

### 已接受：SQLite 音乐库

`library.muse` 是 SQLite 数据库，不是另行发明的二进制格式。歌曲元数据与完整音频文件字节均保存在数据库中，保留存储版本号。普通音频保存输入文件的完整字节；NCM 保存解包后的完整 MP3/FLAC，不在库内另存 NCM 容器。

此前讨论过只保存原文件路径，以及数据库索引搭配独立 media 目录。当前选择数据库收纳音频，以便导入后不再依赖原文件；代价是数据库体积随音乐内容增加。

### 已接受：信息与内容分开存放

逻辑结构如下，实际 DDL 位于 `crates/muse-library/src/schema.sql`：

```text
tracks:         id, title, artist, album, format, duration_ms, netease_id, content_hash (唯一)
audio:          content_hash (唯一), data (完整音频文件 BLOB)
import_sources: source_hash (唯一), track_id
attachments:    track_id, kind, content_hash, mime_type, data；(track_id, kind) 唯一
```

列表查询只读取元数据，音频通过独立操作按需读取。封面和歌词作为歌曲附件独立存放并关联歌曲，列表查询不读取附件内容。`content_hash` 针对最终保存的完整音频文件，`source_hash` 针对导入源的完整文件。两者都采用 SHA-256；普通音频的两者相同，NCM 的两者分别对应容器和解包后的音频。

### 已接受：导入规则

- 导入成功后保留原文件，muse 保存独立的音频副本。
- 单曲的元数据、音频、已成功读取并关联的附件和成功导入记录在同一事务中完整提交后才可见；失败不留下半首可播放记录或已成功导入的标记。
- 同一内容重复导入不增加歌曲或音频副本。
- 存储模块提供 `import`、`list`、`open`、`remove` 四类操作；库打开为 `Library::open`，音频打开为 `open_audio`，具体签名见 muse-library。

### 已接受：两次哈希检查与数据库唯一约束

1. 计算输入文件的 `source_hash`，若已有成功导入记录关联库内歌曲，则跳过音频导入，继续检查缺失的本地附件。文件名和来源路径不参与音频重复身份判断；重复导入同一 NCM 无需再次解包音频。
2. 输入未导入过时，普通音频保持完整文件字节，NCM 解包为完整 MP3/FLAC；计算准备写入库的 `content_hash`。
3. 若音频哈希已经存在，复用已有歌曲，并在事务中关联新的源文件哈希及补齐缺失附件；否则在同一事务中创建音频、歌曲、已成功读取并关联的附件及导入记录。

哈希检查便于提前跳过，数据库唯一约束负责最终保证。遇到重复哈希时返回已有歌曲，不创建第二条歌曲或音频记录。哈希与写入必须针对同一份内容；计算哈希后读取到另一份内容不能作为原哈希的数据保存。

NCM 解包结果与已有 MP3/FLAC 完整字节相同时复用已有歌曲。同名或同网易云歌曲 ID、但库内音频字节不同的文件分别保留，包括不同编码、音质或标签版本。网易云歌曲 ID 仅用于关联信息，不作为去重唯一键。

成功导入记录引用有效歌曲，删除歌曲时一并清理对应记录，使删除后的原文件可以再次导入。失败的导入不留下成功记录，恢复后可以重试。

删除按歌曲标识执行，在一个事务中清理歌曲、对应音频、附件关联和全部成功导入记录；只属于该歌曲的附件内容一并清理，不影响其他歌曲或本地源文件。提交失败时回滚。此处补足已接受的 `remove` 职责，不引入终端删除命令或批量管理功能。

源文件在导入期间可能变化。导入实现须让源文件哈希与普通音频读取或 NCM 解包使用同一份完整输入，音频哈希与最终 BLOB 使用同一份完整音频；可以固定一份输入后继续，或在无法保证一致时将该输入判为失败。不能先计算哈希，再把重新读取到的不同内容写入原哈希对应的记录。当前实现读取一份完整文件内存快照，再计算哈希、解包和提交，不在这些步骤间重新读取源音频。

### 已接受：独立终端应用与内置命令入口

基础界面采用歌曲列表、底部状态栏和命令输入行，`:` 进入命令输入，`:import` 是导入入口。无需启动 Neovim。

### 已确认：本地文件与目录导入

用户已明确第一版导入本地音频文件或目录。应用内命令入口为 `:import <文件路径>` 和 `:import <目录路径>`，目录默认递归扫描子目录。在线歌曲或歌单链接不属于首版范围。当前实现支持 MP3、FLAC 和 NCM。

### 已接受：目录导入的文件级失败处理

目录导入遇到个别音频文件无法读取、损坏或 NCM 无法解包时，记录该文件的失败原因，继续处理其他文件。每首歌独立提交，一首失败不回滚此前已成功导入的歌曲；失败文件不留下成功导入标记，之后可以重试。

任务结束时汇总成功、重复和失败：成功表示新增歌曲，重复表示复用已有歌曲，失败表示该文件未能完成导入。失败项提供文件路径和原因，具体展示形式留待界面设计。已识别的非音频文件不计作音频导入失败；封面、歌词按附件处理。

统计以本次单曲事务的结果为准。附件读取或关联问题作为附加信息，不改变提交成功后的新增或重复分类；附件数据库写入失败仍导致该次事务失败。单文件导入沿用同一分类。库级错误提前停止时，只汇总已处理的输入并另行提示停止原因，不把尚未处理的文件算作新增、重复或文件级失败。

继续处理的前提是音乐库仍可正常写入。若出现库无法打开、存储空间耗尽或写入不可继续等库级错误，则停止本次任务，提示停止原因及已处理结果，保留此前已成功提交的数据。

### 已确认：优先适配网易云音乐的本地下载目录

2026-09-30 对本机 `~/Music/网易云音乐` 的分析发现：87 个 MP3、1 个 FLAC、68 个 NCM、3 个 LRC，以及 `meta/` 下的 89 个封面文件；客户端数据库记录了 88 首下载歌曲。68 首歌曲同时存在 NCM 与同名 MP3，这些同名文件是重复候选，不据此直接合并。

歌曲信息从音频标签及 NCM 元数据读取；歌词可以按同目录同名文件关联，`meta/track-歌曲ID.jpg` 可以按文件中取得的网易云歌曲 ID 关联封面。客户端数据库的数据仅作为此次调查背景，不属于首版导入来源。这是当前本机样本的组织方式，尚未形成覆盖所有下载目录组织方式的兼容性承诺。

已确认 NCM 在导入时解包，库内保存 MP3/FLAC；跨 NCM/MP3 按最终音频的完整字节去重，同曲不同字节的版本保留。已确认随歌曲保存本地已有且能够关联的封面和歌词，首版暂不展示，也不联网补齐。本轮选择下述 Rust 读取器完成解包。

### 已确认：导入信息仅来自指定文件和目录

首版从用户指定的本地文件或目录导入，歌曲信息来自音频标签和 NCM 元数据，关联附件来自文件内嵌内容及导入目录中的文件。不读取网易云客户端数据库，不扫描客户端缓存，不要求本机安装或运行网易云客户端。将下载目录复制到另一台机器后，仍可从其中的有效音频与附件完成导入。

可读取的有效音频不因基础标签缺失而拒绝导入。歌名缺失时使用文件名（不含扩展名）；歌手和专辑缺失时存为缺省值，界面显示 `Unknown`，不从文件名猜测这些字段。网易云歌曲 ID 缺失时仍导入音频，但不匹配需要该 ID 的 `meta/track-ID.jpg`，也不调用客户端数据库或网络补齐信息。

### 已接受：保存本地已有封面和歌词

封面与歌词可以来自音频内嵌内容、NCM 容器内的附件或导入目录内的关联文件。本机样本中的同目录同名 LRC 可关联对应歌曲，`meta/track-歌曲ID.jpg` 可通过已经取得的网易云歌曲 ID 关联封面。不能可靠关联的文件不按歌名猜测归属；本轮采用下述每类一份主附件的实现选择。

成功读取并能够关联的附件随歌曲保存在 `library.muse` 中，保存后不再依赖源文件。不联网下载缺失封面或歌词，不为保存附件而改写普通音频或 NCM 解包后音频的标签，音频内容哈希只针对准备入库的完整音频文件。

附件缺失时正常导入音频；发现的附件无法读取或无法关联时报告相应问题，不阻止有效音频入库。实际数据库写入失败仍按单曲事务和库级错误规则处理。首版只保存附件，界面不提供封面和歌词展示。

重复输入仍复用已有歌曲和音频，但会检查并补齐缺失的本地附件；补齐与来源关联在事务中提交，已有附件保留，相同附件不重复添加。补齐附件仍计作重复歌曲，不计作新增歌曲。这样再次导入能够收纳后来增加的 LRC 或封面，同时保持音频去重规则。

### 已确认：使用 Rust 开发

用户确认项目使用 Rust。播放采用独立 workspace 库并确定后续内置 Rust 播放方向；本轮选择 Ratatui/Crossterm 和 Rust NCM 读取器，随后 native-playback 选择并实现 Symphonia 0.5.5 解码和 Rodio 0.22.2 输出。

### 已确认：独立播放库提供基础接口与可选内置后端

根目录为纯 workspace，muse 二进制位于 `crates/muse`，播放库位于 `crates/muse-playback`，存储库位于 `crates/muse-library`。程序帮助、界面与错误使用英文，用户信息及路径保持原样。最初仅提供 trait 的阶段由 playback-interface 建立；用户现在要求实现后端，native-playback 增加可选 native feature，应用默认启用。基础接口仍可单独以标准库构建。

`Playback` 提供 `load`、`play`、`pause`、`stop`、`seek`、`status`，接收拥有自身生命周期的可读取、可定位音频来源，返回状态、位置和可缺省的总时长。SeekTarget 区分指定时间跳转、快进和快退，seek 返回实际落点并保留播放或暂停意图。库不包含 SQLite、终端界面、NCM 解包或队列职责；歌曲选择及结束后的下一首由主程序决定。内置 Rust 后端已由 native-playback 接入。

### 调研记录：通过 FFI 复用 ncmdump

评估对象为 `taurusxin/ncmdump` 的 1.5.1 版本。其已有 `extern "C"` 接口提供创建对象、导出音频、补写标签和销毁对象四类操作；Rust 可以将 C++ 对象指针视为不透明句柄，在封装内部管理生命周期。

本机已用未修改的上游源码编译出 macOS 动态库，确认四个 C 接口均正常导出并成功链接 TagLib 与 C++ 运行库。该验证仅覆盖本机编译、链接和符号导出，尚未验证 Rust 调用、运行时解包或其他平台。

实际接入仍需处理以下事项：

- 上游 CMake 在 macOS/Linux 上只构建命令行工具，需要增加库构建目标并处理原生依赖的分发。
- 创建对象和补写标签的导出函数没有捕获 C++ 异常，导出音频函数只捕获部分异常；需要在 C++ 接口内转换为错误返回，避免异常穿过 Rust FFI 边界。
- 当前接口仅输出音频文件，没有直接读取元数据、封面或音频流的接口。若要将网易云歌曲 ID 等信息存入 SQLite，需增加读取接口或单独解析元数据，并明确输出数据的所有权和释放方式。
- Rust 封装内部管理原生句柄并通过 `Drop` 释放，对上层提供 `Result` 等安全接口；不将原生指针和内存管理职责交给界面或存储模块。

来源：[C 接口](https://github.com/taurusxin/ncmdump/blob/1.5.1/src/lib/libncmdump.h)、[接口实现](https://github.com/taurusxin/ncmdump/blob/1.5.1/src/lib/libncmdump.cpp)、[构建配置](https://github.com/taurusxin/ncmdump/blob/1.5.1/CMakeLists.txt)、[Rust FFI 文档](https://doc.rust-lang.org/nomicon/ffi.html)。本轮选择下述 Rust 读取器，不引入该 FFI 方案；这份记录保留为技术调查背景。

### 本轮实现选择：存储与导入

- 内部 workspace 库 `muse-library` 提供 `Library::open`、`import`、`list`、`open_audio`、`remove` 与附件读取，沿用工具链和许可证，不独立发布。
- 使用 `rusqlite` 的 bundled SQLite 与 `rusqlite_migration`；首个内嵌 SQL 初始化结构，`application_id` 标识 muse，`user_version` 标识结构版本。写入前拒绝其他数据库和更高版本。手动备份恢复见 `library-backup`，自动破坏性迁移前备份尚未实现。
- 普通音频读取为单文件内存快照，Lofty 识别标签；只收录 MP3（MPEG Layer III）、FLAC 和 NCM。
- NCM 使用 Rust 读取器，参考 ncmdump 1.5.1 的容器字段与变换规则。AES、Base64、字段长度和填充均检查边界，最终完整音频进入同一导入路径，不改写标签或引入 C++/TagLib。参考实现许可随源码与归档保存。
- `open_audio` 返回持有单首完整音频的 `Cursor<Vec<u8>>`，关闭库后仍可读取，满足播放来源 trait 的所有权要求；native-playback 已验证真实解码和本机默认设备输出。
- 每类附件保存首个有效主附件。封面优先级为 NCM、音频内嵌、音频父目录 `meta/track-ID.jpg`、目录导入根部 `meta/track-ID.jpg`；歌词优先级为 NCM、音频内嵌、同目录同主干 LRC。重复输入只补齐缺失类别，已有内容保留。
- 单文件附件只查音频父目录，目录导入限制在指定根内，不跟随目录符号链接或读取越界附件。完整目录扫描后，未关联的已识别 LRC 和 `meta/track-ID.jpg` 作为附件问题报告；中止时不提前判断剩余附件的归属。

这些是用户要求继续开发后作出的实现选择，不称为此前已逐项确认的用户决定。

### 本轮实现选择：终端导入界面

使用 Ratatui/Crossterm，默认库为 `./library.muse`，允许 `--library <路径>` 指定。歌曲按稳定入库标识排序，`j/k` 移动选择、`:` 输入、`Esc` 取消、`:q` 或 Ctrl-C 退出。导入在独立连接的工作线程运行，同时只启动一项任务；结束后刷新列表并保留仍存在的选中歌曲。

导入结果显示新增、重复、失败与附件/扫描问题数量；Tab 切换结果区域，`j/k` 滚动、`h/l` 横向查看路径和原因。退出取消尚未开始的文件，等待当前单曲提交或回滚并恢复终端。打开或读取库失败时明确返回错误。

播放后端与终端接入由 native-playback 实施：Enter 加载选中歌曲、Space 暂停恢复、左右定位十秒、:stop 保留来源归零。曲终停止，故障持续报告；无设备不妨碍导入、浏览和备份。

播放接口的最初建议见 playback-interface/design.md，实际后端与验证见 native-playback。NativePlayback 使用 Symphonia 解码、Rodio 输出、有限 PCM 缓冲和后台控制，加载准备后替换；seek 完成后返回实际落点，旧歌曲版本的操作被拒绝。真实 PCM 消费和本机默认设备检查与跨平台 CI 的构建范围分别记录。

## Risks / Trade-offs

- 数据库包含完整音频 → 导入会额外占用音频体积，不承诺额外压缩效果。
- 内存快照及拥有型来源随单曲体积增加内存占用 → 当前选择完整字节读取，NCM 处理中同时存在容器和解包内容；大文件读取与缓存优化留给后续验证。缓存如被采用，清理不能影响库内音频。
- 导入中断可能留下半成品 → 以单曲事务保证完整提交；个别文件失败继续其他文件，库级错误停止任务并保留此前成功数据。
- 数据库备份可能涉及运行中的日志文件 → 后续 `library-backup` 变更采用 SQLite Online Backup API 保存已提交一致快照，验证后发布独立单文件；不依赖运行中主文件复制。

## Migration Plan

当前建立第 1 版音乐库，尚无已发布历史版本迁移。启动使用内嵌初始化 SQL 和 `PRAGMA user_version` 保存与应用版本独立的结构版本，脚本和版本在同一事务中提交，失败回滚，库版本过高时拒绝修改。

已选择 `rusqlite` 搭配 `rusqlite_migration`，SQL 编入二进制，后续只追加迁移，不修改已发布脚本。库身份识别与错误提示由存储模块负责。普通元数据迁移尽量不重写音频表。后续 `library-backup` 变更已提供手动一致备份及恢复到新路径；自动破坏性升级前的备份触发、命名和保留策略尚未实现。

### 已实施：最小播放流程

native-playback 已实现选中播放、暂停恢复、快进快退和曲终停止。以下具体按键及曲终停止是本轮实施选择，自动连播或独立队列仍在范围外。

| 操作或场景 | 建议行为 |
| --- | --- |
| Enter 播放选中歌曲 | 打开库内音频，加载成功后调用播放；当前歌曲身份与真实加载结果一致 |
| Space 暂停或恢复 | Playing 时暂停、Paused 时恢复；Ready 或 Finished 从头开始，Empty 提示未加载 |
| 快进、快退或指定时间 | 向播放库提交相对偏移或绝对位置，用返回的实际落点更新进度；暂停仍暂停，换歌后的过期定位请求丢弃；按键和步长由应用决定 |
| 自然结束 | 保留当前歌曲与 Finished，不自动切换；再次播放可从头开始 |
| 加载或播放失败 | 显示原因，不假报正在播放；旧来源与错误恢复依照最终选定的接口契约 |
| 导入期间播放 | 已有音频来源独立于导入连接，歌曲选择和暂停恢复继续可用 |
| 退出 | 先停止输出并释放播放资源，再完成当前单曲导入的退出规则 |

### Playback verification and future reader optimization

NativePlayback now decodes the owned library source. Real PCM tests and macOS device tests passed; a terminal session played after removing the source file and kept controls available during import. Detailed results and platform limits are recorded in native-playback/design.md. Reader optimizations below remain future work.

| 读取方案 | 后续验证要回答的问题 |
| --- | --- |
| 当前完整字节内存读取器 | 较大 FLAC 的峰值内存是否可接受，切换后前一首内容是否释放 |
| 拥有数据库资源的读取器 | 能否满足 `Read + Seek + Send + 'static`，读取期间是否妨碍导入，如何维持生命周期 |
| 从库重建的临时文件 | 源文件移走后能否播放，切换、退出与异常路径如何清理，清理不影响库内音频 |

候选读取器不能泄露 SQLite 类型给播放库；缓存仅为从库重建的派生数据。

Completed backend checks cover MP3/FLAC loading, playback, pause/resume, absolute/relative seeks, boundaries, paused intent, completion, invalid replacements, persistent faults and cleanup. Old PCM/completion cannot affect a new session, and stale controls cannot affect a new generation. The library/device check and terminal session removed the original file before playback. NCM and attachments still use the existing import/storage path.
